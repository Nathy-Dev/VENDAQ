## Documented interface versus unknown guarantees

| Area | Documented facts | PIPELIXR consequence / remaining verification |
| --- | --- | --- |
| Webhooks (E1) | Envelope includes `event`, `data`, `instanceId`, `instanceToken`. Subscription categories differ from emitted names: `MESSAGE` -> `Message`, `SEND_MESSAGE` -> `SendMessage`, `CONNECTION` -> several lifecycle events. Message metadata uses `data.Info`; receipts contain `MessageIDs`, root `state` and ISO timestamps. | Authenticate against a stored instance binding; explicitly normalize categories/events and timestamp units. Do not route by display name. The token field is not an HMAC/replay guarantee. |
| Receipt/identity/retry limits (E1) | Examples include alternative LIDs. Receipt examples do not establish Status-view completeness. The guide expects a 2xx response within 30 seconds and 30-second retry spacing, but says five retries in one section and five attempts in another. | Keep identities opaque; qualify Status independently. Persist before acknowledging. Verify retry count and exhaustion/recovery rather than promise unlimited redelivery. |
| Sending (E2) | `POST /send/text` accepts `number`, `text` and optional `id`/`delay`. The response schema declares `messageId`, while the example carries `data.Info.ID`. | Preserve the actual returned provider ID behind a normalized send result. Caller-supplied `id` is a useful candidate for correlation; the page does not specify repeat-ID deduplication, collision scope or timeout recovery. Do not label it proven idempotency. Test both response descriptions against the pinned build rather than silently guess. |
| Message lookup (E3) | `POST /message/status` accepts an `id`; the page describes retrieval and missing-message errors. | Candidate reconciliation mechanism when an ID is known. The page does not prove indexing latency, retention or that a missing result means the message was never submitted. Never auto-resend an unknown send based on a single negative lookup. |
| Connection/authentication (E4, E7) | The connection API describes `POST /instance/connect`, subscription/webhook configuration and API-key authentication, including global or instance-specific keys. | Establish the deployed tenant-selection/credential contract. Do not send an instance display name as a credential or expose a global key. Outbound API authentication does not authenticate incoming webhook requests. |
| Instance creation (E5) | The endpoint-specific request describes `name`, `token` and optional proxy settings. | This is closer to `buildCreateInstancePayload` than the installation page's alternative example. Treat endpoint-specific schema as a starting point, not proof of deployed behavior. |
| Documentation inconsistencies (E2, E4, E5, E6) | Installation examples use `instanceName`/`integration`, while the create reference uses `name`/`token`. The send OpenAPI has empty security metadata but documents unauthorized errors. Connection guidance and reference differ in explicit instance-header coverage. Installation documents a deployment-local Swagger UI at `/swagger/index.html`. | Do not follow autogenerated examples as evidence that sending is unauthenticated. Compare deployed Swagger, credential behavior and redacted fixtures before enabling integration; reconcile rather than accumulate speculative fallbacks. Public documentation resolves discovery, not runtime qualification. |
| Seller actions (E8) | The reviewed Go index does not establish a self-chat interactive-action callback contract. | Do not substitute Evolution API button endpoints or assume a subscribed `BUTTON_CLICK` name proves support. Native one-tap actions remain a qualification item; the authenticated web fallback still needs owner approval if required. |

## Concrete gaps in the existing repository

These are static comparisons, not tests against the deployed server:

- `convex/http.ts:40`: routing omits the documented top-level instance fields. A conforming body without legacy routing headers can be acknowledged as skipped before ingestion. This is more concrete than the earlier broad contract uncertainty.
- `convex/http.ts:164` and `convex/http.ts:631`: uppercasing does not insert underscores; several lifecycle/outbound event names therefore miss the existing branches. The current outbound branch also handles Status posts rather than a general owner-reply stream. Qualification must prove seller replies reach cancellation logic.
- `convex/http.ts:102`: receipt extraction assumes scalar IDs and ignores the documented ID array; useful delivery evidence can be lost. Do not turn ordinary DM receipts into viewer observations.
- `convex/evolutionGoClient.ts:275`: the request helper uses one `apikey` value and optional custom token; bind real stored credentials and instance identity before selecting this API mode. Existing string fallbacks are not an authorization design.
- `convex/evolutionGoClient.ts:517`: text sending supplies no caller ID and discards the response. Add the typed result/correlation boundary only in the approved implementation phase; do not assume provider-side duplicate suppression from the optional field.

## Phase 1 qualification and implementation update

The current public Evolution Go documentation and OpenAPI were rechecked on 2026-10-28. The Phase 1 client now:

- uses only `/instance/all`, `/instance/create`, `/instance/connect`, `/instance/status`, `/instance/qr` and `/instance/disconnect`;
- defaults to instance-token `apikey` authentication and requires an explicit alternate-mode configuration;
- parses the documented `data.Connected`, `data.LoggedIn` and `data.Qrcode` shapes;
- subscribes only to message, owner-message, receipt, connection and QR categories;
- requires both provider qualification flags before connect;
- never calls send, read-marking, reaction, presence, media-download or AI endpoints.

The exact deployed build identifier and redacted Swagger fixtures remain operator qualification items. No deployed provider was called during local implementation.

1. Fake the documented message/owner/lifecycle/receipt envelopes with synthetic identities, including replay, alternate identity, multiple receipt IDs and ISO timestamps. Assert tenant resolution, persistence and cancellation without network sends.
2. Verify invalid instance credentials cannot write or route across tenants. No raw credential-bearing payloads in logs, queue envelopes or committed fixtures. Missing authentication policy must fail closed.
3. Test durable acknowledgement, timeout/retry exhaustion and malformed/unsupported events without executing provider operations. Do not copy media or unrelated groups merely because a subscription permits them.
4. Before real provider integration, record the deployed build and confirm its Swagger/auth/event contract. Any eventual send-ID/duplicate/status-lookup experiment requires a separately approved non-production sending test, never Phase 2 read-only traffic.
5. Keep ambiguous sends blocked until acceptance or definite non-submission is established. Retain separate accepted/delivered/failed/unknown states and the full ADR 0002 safety/attribution policy.

## Review outcome

The documentation-source question is closed. Deployed version, authentication and text-send behavior are now qualified in the [2026-10-28 report](evolution-go-send-qualification.md): repeat caller IDs enter the send path, caller IDs cannot be reconciled through `/message/status`, and timeout results remain unknown. Status/self-chat capabilities remain separate qualification items. The owner approved the no-worker Convex design; neither the documentation link nor the live transport test grants permission to enable automated production sending.

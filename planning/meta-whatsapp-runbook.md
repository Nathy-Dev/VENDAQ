# WhatsApp Cloud API Coexistence runbook

## Scope

One existing WhatsApp Business app number and one Meta Messaging account per Pipelixr workspace. The account and phone cannot be bound to two workspaces. The Business app remains usable, and eligible app replies appear in the Pipelixr inbox. The signed webhook accepts live 1:1 messages, app echoes, contact changes, shared history, delivery statuses, and account offboarding. The inbox sends plain-text service replies; optional assistant replies continue to require separate per-workspace authorization. No template sends, bulk campaigns, groups, statuses, calls, edit/revoke mirroring, or outbound attachments are enabled. Messages without a usable phone number can appear when Meta provides a business-scoped identity, but are not sendable from Pipelixr. Live images and voice notes can use the existing opt-in processing pipeline; other media and history attachments are shown as text/captions or review placeholders rather than downloaded.

## Meta and Convex setup

1. Use a verified Meta business and approved Tech Provider/Solution Partner app. Configure Facebook Login for Business with a WhatsApp Embedded Signup configuration, a business integration token, and the required Advanced Access permissions (including `whatsapp_business_management` and `whatsapp_business_messaging`; follow the app's review checklist for additional permissions). For staging, use separate Meta and Convex environments and a real, eligible WhatsApp Business app pilot number; do not move a customer's live number to rehearse.
2. Set the exact HTTPS frontend origins in Meta's **Allowed Domains** and relevant URLs in **Valid OAuth Redirect URIs**. Enable JavaScript SDK login and confirm the app is in the correct mode for the pilot users. Check Embedded Signup v5 for the configured Meta app, and pin a Graph version supported by that app. Have the business add its payment method in WhatsApp Manager if required by its onboarding/partner arrangement; a Pipelixr payment does not cover Meta charges.
3. Deploy the additive Convex schema/backend and the matching frontend with both Meta flags off. On the intended Convex deployment, set `META_WHATSAPP_APP_ID`, `META_WHATSAPP_CONFIG_ID`, `META_GRAPH_VERSION`, `META_WHATSAPP_APP_SECRET`, a separately generated high-entropy `META_WHATSAPP_VERIFY_TOKEN`, `SESSION_ENCRYPTION_KEYS`, `SESSION_ENCRYPTION_KEY_VERSION`, and `IDENTITY_HASH_KEY`. Do not put these secrets in browser variables, client logs, or source control. Keep old encryption key versions available while old ciphertext still exists; do not rotate the identity key in place without a migration.
4. Configure Meta's WhatsApp webhook callback as `https://<deployment>.convex.site/api/webhook/meta/whatsapp`. Use the Convex **HTTP Actions** host, not the `.convex.cloud` client host or the frontend origin. Verify the callback with the configured verify token. Subscribe the WhatsApp object to `messages`, `smb_message_echoes`, `smb_app_state_sync`, `history`, and `account_update`. Do not insert a proxy that changes the signed request body. Pipelixr subscribes the app to each approved Messaging account after signup; it does not register or deregister the already-registered number.
5. Set `META_WHATSAPP_ENABLED=true` to expose signup. Leave `META_WHATSAPP_SEND_ENABLED=false` until the webhook/historical-data checks pass. Configure a first workspace through `/onboarding/connect` or **Settings → Connection**. Select the existing number in Meta, use the Business app to confirm the link, and select whether to share chat history. Keep the app open during sync. The owner may need to relink supported companion devices. If testing a migrated workspace, first revoke/reset the Evolution session and verify the old remote instance is gone; dual ingestion of the same number is not supported.

## Release gates

- In staging, exercise real Chrome/Safari popup behavior from a direct page load and from in-app navigation. Confirm cancellation and ordinary Cloud API signup do not bind the number. Verify that the connected number still works in the Business app, and that incoming customer messages and app replies land in the same Pipelixr conversation without duplicates.
- Confirm contact/history sync within Meta's onboarding window using both a shared and a declined history case. Confirm imported messages are limited by workspace retention and create no assistant sends or marketing consent. If inbound processing is enabled, test one image and one voice note. Confirm a different account or phone cannot see or modify this workspace.
- Enable `META_WHATSAPP_SEND_ENABLED=true` in staging. From a separate personal test number, message the pilot business, reply in Pipelixr, and observe the result on the receiving device and the status in the inbox. Verify an opt-out, a closed 24-hour window, and disconnect each block outbound sends. Rehearse timeout, reordered statuses, and webhook retries; an uncertain send must never be retried automatically. If moving to production, repeat with a controlled pilot before making signup available broadly.
- Rehearse local disconnect and app-side offboarding; confirm scheduled work is fenced by the session generation. Pipelixr disconnect stops local processing and drops its credential. To remove the remote link, use **WhatsApp Business → Settings → Account → Business Platform → Disconnect Account**. If the remote event is absent, inspect the Meta webhook delivery log and do not try to bypass the existing binding.

## Operations and rollback

- Alert on Meta webhook non-2xx responses, Convex ingress/queue errors and dead letters, growing backlog, connection auth failures, unconfirmed sync, and failed/unknown dispatches. Inspect `inboundEvents`, `whatsappSessions` (states and sync request IDs), and `assistantDispatches` (state/Meta delivery code) through restricted access. Use the webhook correlation ID for errors without sharing payloads, tokens, or customer messages. A history status of received means Meta's chunks were durably queued, not that every item was retained or processed.
- For token expiry or loss of Meta permissions, reconnect the same account/phone. If sync is `Unconfirmed`, do not automatically replay the one-time sync; check Meta delivery, request IDs, and merchant consent. If Meta requires a new sync, coordinate app-side offboarding and repeat Embedded Signup. A **delivery unknown** conversation must be checked and, if needed, handled in WhatsApp directly; an eventual verified callback may clear the block.
- Roll back new sends first with `META_WHATSAPP_SEND_ENABLED=false`, then new signups with `META_WHATSAPP_ENABLED=false`. Existing webhook ingestion remains active so in-flight statuses can settle. To stop it for an account, use local disconnect or complete app-side offboarding. Roll back to a schema-compatible backend; do not remove validators/indexes while stored Meta records still use them. If an app secret is compromised, disable sending, rotate it in Meta and Convex, and verify signed callback delivery again.
- Before launch, have the operator confirm data handling, retention, consent, customer support, and provider disclosures for the actual deployment.
